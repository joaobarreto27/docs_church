## 1. Diagnóstico e Problemas Atuais

O arquivo `src/services/neon.ts` possui um nome enganoso (chama-se `neon.ts`, sugerindo conexão direta com o banco), quando na verdade é o cliente HTTP do frontend que conversa com as rotas serverless da Vercel (`/api/room`, `/api/block`, `/api/sync`). Ele mistura:
1. Máscaras de formatação de string e gerador aleatório de código de sala (`formatRoomCodeMask`, `generateRoomCode`).
2. Mecanismo genérico de retentativa assíncrona contra instabilidade de Wi-Fi (`withRetry`).
3. 14 funções de API distintas contendo lógica de cabeçalho `Authorization: Bearer <token>` duplicada.
4. Falta de separação entre o que é utilitário de domínio (código/máscara) e o que é comunicação de rede.

---

## 2. Diretrizes de Arquitetura & Patterns

- **Repository Pattern (`/design-patterns`):**
  - Isolar as chamadas de rede em `LiturgicalRepository` ou `liturgicalApi.ts`.
  - O resto da aplicação interage com contratos e interfaces tipadas, sem se preocupar com endpoints e cabeçalhos HTTP.
- **Fronteira Rígida do Bundle (`/secure-architecture` - Lei 1 e Lei 2):**
  - O cliente frontend NUNCA deve importar `@neondatabase/serverless` ou bibliotecas nativas de banco.
  - Todas as chamadas continuam usando endpoints REST parametrizados.
  - Renomear o serviço para afastar a falsa impressão de driver de banco no cliente.
- **Prevenção de IDOR e Autenticação (`/secure-architecture` - Lei 3 e Lei 4):**
  - Garantir que todas as mutações administrativas repassem o `sessionToken` (gerado por HMAC-SHA256 no backend) e o `roomId`.

### REQUISITOS DETERMINÍSTICOS:

2. **CRIAÇÃO DE `httpClient.ts`:**

3. **CRIAÇÃO DE `liturgicalRepository.ts`:**
   ```typescript
   import { Room, LiturgicalBlock, UserRole } from '../../types/liturgy';
   import { getApi, postApi } from './httpClient';

   export const liturgicalRepository = {
     async joinRoom(code: string, role: UserRole, pin?: string) {
       return postApi<{ success: boolean; room: Room; token?: string; error?: string }>('/api/room?action=join', { code, role, pin });
     },
     async getRoomByCode(code: string) {
       return getApi<Room>(`/api/room?action=by-code&code=${encodeURIComponent(code)}`);
     },
     async getBlocksByRoomId(roomId: string) {
       return getApi<LiturgicalBlock[]>(`/api/room?action=blocks&roomId=${encodeURIComponent(roomId)}`);
     },
     async updateBlock(blockId: string, content: any, roomId: string, token?: string) {
       return postApi<{ success: boolean; block: LiturgicalBlock }>('/api/block?action=update', { blockId, content, roomId }, token);
     },
     async appendItems(blockId: string, newItems: any[], roomId: string, token?: string) {
       return postApi<{ success: boolean; block: LiturgicalBlock }>('/api/block?action=append', { blockId, newItems, roomId }, token);
     },
     async setAlert(roomId: string, alert: string | null, token?: string) {
       return postApi<{ success: boolean; room: Room }>('/api/room?action=alert', { roomId, alert }, token);
     },
     async setPage(roomId: string, page: number, token?: string) {
       return postApi<{ success: boolean; room: Room }>('/api/room?action=page', { roomId, page }, token);
     },
     async resetService(roomId: string, newTitle: string, token?: string) {
       return postApi<{ success: boolean; room: Room }>('/api/room?action=reset', { roomId, newTitle }, token);
     }
   };
   ```

4. **COMPATIBILIDADE EM `src/services/neon.ts`:**
   - Reexportar as funções a partir de `./api` para permitir migração incremental sem quebrar o build.
